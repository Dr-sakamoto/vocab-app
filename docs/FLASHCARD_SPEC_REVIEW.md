# フラッシュカード仕様の検証

Gemini と議論した「英単語学習アルゴリズム 仕様書」を、現行コードと
[`CLAUDE.md`](../CLAUDE.md) のコアバリューに照らして検証した記録。

## 結論

**問題意識は正しい。仕様は 4 分の 1 だけ採用する。**

| 仕様の項目 | 判定 | 理由 |
| --- | --- | --- |
| フェーズ1 高速周回（フラッシュカード） | ⭕ 削って採用 | インプット欠落は実在する。ただし「1日1周3000語」「2.5分+0.5分×20」は外す |
| フェーズ2 ステップ1 4択テスト | ❌ 却下 | `CLAUDE.md` の禁止事項に抵触。過去に撤去済みの機能の復活 |
| フェーズ2 ステップ2 記述式＋AI柔軟判定 | ✅ 実装済み | 新規作業なし |
| 分散学習（SRS） | 🟡 別PR | 価値は高いがスキーマ変更を伴う。単独で切る |

## 前提の確認：インプット補助は本当に無いのか

**無い。指摘は正しい。**

現行の唯一の接触経路は「失敗してから答えを見る」だけ:

- `app/page.tsx` は単一画面で、出題 → タイピング → 判定 → 次、のループしか持たない
- 初見の単語（`stats[i]` が `{correct:0, wrong:0}`）も他と同じく出題される
- 訳が表示されるのは不正解時の赤枠（`TypingAnswerRow.tsx:155`）か「？」を押したとき
- 一度見た訳をもう一度「眺める」手段は存在しない

つまり初見単語は **確定で 1 回不正解を踏まないと意味を知れない**。
`wrong` が積まれ、ストリークが切れる。インプットが失敗のペナルティと
抱き合わせになっている。ここは埋める価値がある。

## 却下・修正が必要な点

### 1. 4択テストは禁止事項に抵触する（却下）

`CLAUDE.md`:

> 記述式回答を選択式に置き換える変更（AI判定の存在意義を失わせる）

仕様では 4択 は置き換えではなく「記述式の手前の段」だが、実質的に
**初見〜定着前の最も重要な期間を再認テストで通過させる**設計であり、
AI判定が効くのは記憶が固まった後だけになる。順序が逆。

加えて選択式は既に一度撤去されている。`useGameSession.ts:42-46` に
コメントだけが残骸として残っており、そこには当時判明した罠も書かれている:

> 選択式では表記ゆれ審査が不要なうえ、他の単語の訳である
> ダミー選択肢が「別解」として誤承認される恐れがあるため API を呼ばない。

ダミー選択肢の生成器（他の単語の訳から誤答を作る）を再実装することになり、
`SYNONYM_GROUPS`（`lib/answerEvaluation.ts`）に同義語として登録済みの訳が
ダミーに選ばれると「誤答が正解になる」事故が起きる。撤去した機能を、
撤去理由を残したまま戻すことになる。

### 2. 「1日1周3000語」はアンロック設計と両立しない

- 語彙総数は **3440 語**（`lib/vocab/basic.ts` 1500 + `advanced.ts` 1940）。仕様の 3000 は概数
- 現行は `INITIAL_POOL_SIZE: 60` から始まり、10問セットで正答率 80% 以上なら +30、
  100% なら +50 ずつ解放（`lib/constants.ts`, `app/page.tsx` の `finishSet`）
- 全語到達には良好なセットを 70〜110 回積む必要がある

フラッシュカードが初日に全 3440 語を流すなら、Tier 1 → MASTER の梯子
（`lib/poolTier.ts`）と段階的アンロックは意味を失う。これは
コアバリュー3「継続性 — 段階的アンロック」の土台そのもの。

さらに [`MONETIZATION.md`](../MONETIZATION.md) の無料枠は **単語プール上限 300 語**。
「1日1周3000語」は定義上プレミアム専用機能になるか、さもなくば
無料/有料の線引きが崩れる。どちらを取るかの判断が仕様に含まれていない。

### 3. 60分の儀式はコアバリュー1に反する

コアバリュー1は「1問ごとの割り込み・意思決定・画面遷移を増やさない」。

- 「2.5分 + 0.5分」× 20セット ＝ **強制休憩による割り込みが20回**
- モード選択（周回 / テスト）＝ ループ開始前の意思決定と画面状態が新設される。
  現行は起動した瞬間に 1 問目が出ており、選択は 0 個

固定ペースの自動送り自体は意思決定を消すのでフロー向きだが、
その外側に巻かれた儀式が逆を向いている。

### 4. 既知マークは取り消せない

「スクロールは止めず、既知の単語のみワンタップでマーク」は、
誤タップが**そのまま次回除外**に直結する。仕様に取り消し手段が無い。
取り消しを足せば割り込みが増える。

また `WordStat` は `{ correct, wrong }` しか持たない（`lib/types.ts`）ので、
「既知フラグ」は新しい永続データになる。localStorage、`word_stats` テーブル、
`lib/sync.ts` のマージ規則、`lib/wordProgress.ts` の移行処理すべてに波及する。

### 5. 「軽微なスペルミス」は本アプリでは成立しない

仕様の判定要件:

> 軽微なスペルミスは一律の不正解とせず、「意味は正解（スペル注意）」として…

本アプリでユーザーが入力するのは **日本語訳** であって英単語ではない。
スペルミスという概念が無い。実際の課題は表記ゆれ・同義語であり、それは
**既に実装済み**:

- `lib/answerNormalization.ts` … 正規化
- `lib/answerEvaluation.ts`（402行）… kuromoji 形態素解析 ＋ 60組超の `SYNONYM_GROUPS` ＋ 品詞違反検出
- `app/api/ai-review/route.js` … Gemini による最終判定と承認回答の学習

つまりフェーズ2ステップ2 は新規作業ゼロ。仕様がそれを知らないだけ。

### 6. 分散学習（SRS）はデータモデルが未対応

仕様の中で単独の価値が最も高いのはここ。ただし現状:

- `WordStat` に時刻が無い。あるのは通算 `correct` / `wrong` のみ
- `word_stats.updated_at` はトリガ更新の書き込み時刻で、一括同期のたびに
  上書きされる。**最終復習日としては使えない**
- `lib/sync.ts` のマージは `Math.max` 前提。日付にはそのまま適用できず、
  衝突規則を別に決める必要がある
- 出題重み付け（`useVocabPool.ts` の `getQuestionWeight`）は
  「間違えた語を厚く出す」という時間非依存の近似を既に行っている。
  SRS はこれを時間軸付きに置き換える改修になる

新カラム ＋ マイグレーション ＋ 同期規則 ＋ スケジューラで、
単独で 1 PR に値する規模。フラッシュカードとは独立に実装できる。

## 仕様全体のスコープ判定

仕様をそのまま実装すると、以下 4 サブシステムが同時に入る:

1. フラッシュカード描画とタイマー
2. 既知フラグの永続化（localStorage / DB / 同期 / 移行）
3. 選択式モードとダミー選択肢生成器
4. SRS スケジューラとスキーマ変更

`app/page.tsx`・hooks・`lib/types.ts`・`supabase/migrations/`・`lib/sync.ts` に
横断的に触ることになり、`CLAUDE.md` の「1PRにつき1つの改善」
「大規模リファクタリング禁止」に真っ向から反する。

## 採用する形

**v1: 解放済みプール限定のフラッシュカード（新規永続データなし）**

- 対象は **解放済みプールの語のみ**。アンロック設計と無料枠の線引きを壊さない
- 固定ペースの自動送り（意思決定ゼロ、フロー向き）
- **休憩サイクルは持たない**。ユーザーがやめたいときにやめる
- 既知マークは持たない。`getQuestionWeight` の `confidenceBoost`
  （`correct >= 2 && wrong === 0` で出題頻度を 0.45 倍）が既に同じ役割を果たしている
- 結果として localStorage もスキーマも同期も一切変更なし ＝ 1 PR に収まる

**その後の別PR: SRS。** 価値は最大だがスキーマ変更を伴うため単独で切る。

**永久に入れないもの: 4択テスト。**
